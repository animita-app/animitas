# Insight Presets Implementation - Complete

## What Changed

### 1. Database Schema (`17_insight_presets.sql`)
**New Table: `insight_presets`**
- Stores kind-specific preset insight items
- Structure: `(id, kind_id, category, label, created_by, created_at)`
- Each preset is unique per kind/category/label combination
- RLS policies: Everyone can read, authenticated users can insert

**Updated: `site_insights`**
- Removed `subcategory` column (simplified from 4-level to 3-level structure)
- New unique constraint: `(site_id, category, label)`
- Structure: `(id, site_id, category, label, created_at)`

**Seeded Data**
- Animita presets (memorial, ritual, ofrenda, forma, escala categories)
- Santuario-vial presets (tipo de evento, rol de víctima, lugar, etc.)

### 2. Frontend Types
**Updated `types/heritage.ts`**
```typescript
// SiteInsight - simplified
```

### 3. New Hook: `use-insight-presets.ts`

- `addPreset(category, label)` - Creates new preset (adds to global pool)

## How It Works

### User Flow: Creating Insights
1. User opens an animita/santuario (site detail view)
2. Click insight chip → opens kind-specific preset dropdown
3. Presets are organized by category (e.g., "Causa de muerte: Suicidio")
4. User selects items OR types custom text to create new ones
5. New custom items are added to the global preset pool
6. All selected items saved to `site_insights` table

### Data Flow: Presets vs Site Insights
- **Presets** (`insight_presets`): Kind-level library of available items
- **Site Insights** (`site_insights`): Which presets are assigned to THIS site
